# microduck-cli: env, teach, operate, rules

> microduck-cli sets up a MicroDuck environment (sim or real), trains and publishes policies through `microduck_rl`, drives the duck directly over robotd's JSON-RPC, and runs a data-only rules layer (events -> rules -> actions) — one CLI that any agent or human drives, implementing the upstream pollen-robotics docs and pointing users at them.
> instruction: Verify by running the same 'duck' verbs against a --fake daemon in tests and a --sim daemon on the dev box; implement by keeping robot control behind one JSON-RPC client seam and one engine TargetSink, with sim vs real being only a socket path.

## Audience

- Two kinds of operator, one surface: (1) AI agents on the AgentCulture mesh (any backend — the colleague resident, Claude Code, Codex, Copilot) that set up the duck's environment, author rules, inject ad-hoc instructions, and run training without a human at the keyboard; (2) the human who owns the duck and does the same things interactively. Every verb serves both: --json and --apply for agents, TTY confirmation and readable text for the human.

## Before → After

- After: A person or agent runs one CLI to (a) bring up a MicroDuck — today the MuJoCo twin driven by the real robotd, later a physical duck at the same socket contract — and know from 'env doctor' exactly what is missing; (b) operate it in robotctl's own words plus velocity 'move', with motion gated; (c) train, export, publish and install a policy through `microduck_rl`'s documented pipeline on a local GPU box or HF Jobs; and (d) run an off-board engine whose data-only rules turn observed events into injected instructions, with agents able to inject ad-hoc instructions through the same admission path. The duck keeps whatever autonomy upstream ships; this layer sits above it.

## Why it matters

- Today driving a MicroDuck means reading two upstream repos, hand-assembling a sim from a branch, a params file, a dlopen'd ONNX runtime and a socket path, and typing raw robotctl or gamepad input; teaching it means a separate GPU project with its own conventions. None of that is agent-operable and all of it is re-derived per person. One CLI that implements those docs — and links to them — lets any agent or human spare that work, and gives the engine that neurosymbolic-system will be extracted from a second robot to generalise against.

## Requirements

- Transport is JSON-RPC 2.0 NDJSON over robotd's unix socket, implemented with stdlib socket+json only. The socket path is configurable (--socket / `DUCK_SOCKET`): in simulation it is the short state-dir path robotd --sim was started with (upstream's scripts/duck-sim uses $`DUCK_SIM_STATE`/duck-a.sock; a unix path is capped at ~108 bytes), and when a real duck exists the same client points at a forwarded /run/robotd.sock ('ssh -L …', cheatsheet-dev.md). Method names, `API_VERSION`, the 'hello' handshake, error codes and `JOINT_NAMES` come from duck-ipc-proto/src/lib.rs and are re-checked at connect. Continuous intents (robot.move/head/pose/mouth/sound hold) are sent as notifications at 20–50 Hz, last-writer-wins and expiring; discrete ones (robot.do/look/stop/enable/init/relax) as answered requests — the split the proto crate documents.
  - honesty: A daemon answering hello with a newer `API_VERSION` runs; an unknown method answers `METHOD_NOT_FOUND` and is logged as a named drop, never a traceback; a daemon whose `JOINT_NAMES` or obs/action lengths differ from the client's table refuses to start the engine with both numbers in the message.
- Addressing follows upstream's simulation naming: a duck is a name (duck-a, duck-b …) that resolves to <state-dir>/<name>.sock (and <name>-tof.sock), the convention scripts/duck-sim establishes; `DUCK_SIM_DUCK` / --duck select one. duckctl (BLE, 'never on a robot') is wrapped only when a real duck exists — it is not a sim transport. The env doctor names exactly what is missing for the sim stack (a microduck clone on sim-remote-io, cargo/rust ≥1.89, a built robotd+robotctl, a `microduck_rl` .venv with libonnxruntime, a short state dir, a free body port) with the upstream doc line as the remediation.
  - honesty: Given a state dir and a name, the CLI resolves <state>/<name>.sock without any network or BLE call; env doctor on a box with no microduck clone, no cargo, no RL venv or no libonnxruntime lists each missing item with the upstream doc line and exits 2.
- The operate surface uses robotctl's words so a command learned on the robot works here: robot init/relax/do/mode/look, policy list/load/add/remove/reset/search/check/update, pad status/bindings/bind/reset, health, monitor (--json NDJSON), configure --list, quack. It adds one verb robotctl lacks — a velocity 'move' driving robot.move with the deadman refreshed at intent rate, the way padd and the WebRTC console do — and every verb takes --json.
  - honesty: Every verb name and flag in the duck noun matches a robotctl subcommand of the same name (robot init/relax/do/mode/look, policy \*, pad \*, health, monitor, configure --list, quack) plus exactly one addition, move; a table test pins that list against robotctl's Namespace enum.
- Every verb that moves or de-energizes the duck is gated the arm101 way: confirm on a TTY, print a zero-side-effect dry-run plan on a non-TTY without --apply, proceed on a non-TTY with --apply (agent mode). Applies to init, relax (which additionally keeps upstream's --yes semantics), do, move, mode, policy load/add/reset, and pad bind. Upstream's own safety wording is surfaced verbatim: 'init moves every joint — have the robot on its stand', 'relax cuts power and the robot collapses', 'stop zeroes intents and is NOT an emergency stop', 'nothing a stranger publishes is verified by anybody'.
  - honesty: Each gated verb has three tests: TTY without --apply prompts, non-TTY without --apply prints a plan and sends nothing (asserted on a --fake daemon's call log), non-TTY with --apply sends; the four upstream safety sentences appear verbatim in the verb's dry-run output.
- The teach/train lane orchestrates `microduck_rl` by its documented commands, never by importing it: env check (CUDA GPU, uv, Python 3.12 (<3.13 pinned by bam), `UV_HTTP_TIMEOUT`=600 on ARM, hf auth, optional wandb), 'uv run list-envs', the mandatory 64-env/5-iter smoke test, 'uv run train <task> \[--hf-jobs\]', 'uv run play', 'uv run scripts/export.py' (the only safe ONNX path — normalizer baked in), 'uv run publish' (schema-2 manifest, \[1,61\]->\[1,14\] gate), then 'robotctl policy add|load' on the duck. The CLI plans and sequences that pipeline, records the artifacts (task id, run path, checkpoint, ONNX, HF repo), and points at AGENTS.md for reward design.
  - honesty: The train lane never imports `mjlab_microduck`; each stage is a subprocess whose argv equals the upstream-documented command, and the lane refuses to start a long run whose 64-env/5-iteration smoke test has not passed in this session or a recorded artifact.
- The rules layer follows reachy-mini-cli's shape: data-only TOML — \[\[react\]\] (when <predicate> then run <action>), \[\[inhibit\]\], \[modes.<name>\] — predicates as field/op/value over a sense snapshot (never code), unique ids, `cooldown_s`, hysteresis, bounded `duration_s`, two-layer per-id merge (shipped resource + box-local overlay with 'enabled = false' tombstones), fail-closed validation, and 'rules list/check/overview' verbs. Duck sense fields are derived from robot.state / robot.health / pad.input / tof.frame / chorale.heard (fallen, projected gravity, battery fraction, hottest servo, loop Hz, pad buttons, ToF nearest, nearby-duck beacons); actions are robotd intents (do <skill>, look, move, sound/quack, stop, mode).
  - honesty: RulesConfig.`from_dict` refuses every documented bad shape (unknown field, callable value, unknown skill, unknown predicate field/op, negative cooldown, duplicate id, unbounded looping) with the rule id in the message; a two-layer merge test proves per-id override and enabled=false tombstones survive an upgrade of the shipped layer.
- Duck verbs land as noun groups in `microduck_cli`/cli/`_commands`/ following the cli.py pattern (`parser_class`=type(p), own 'overview', CliError-only failures, `emit_result`/`emit_error` split), with engine logic in sibling packages (`microduck_cli`/duck/, /rules/, /train/) and argparse wiring only in `_commands`/. Proposed nouns: 'env' (setup + doctor for sim/real/training), 'duck' (operate), 'policy' (train→export→publish→install pipeline), 'rules' (the neurosymbolic layer). Each new verb updates explain/catalog.py ENTRIES, overview.py `_VERBS` and learn.py in the same change, and 'teken cli doctor . --strict' stays green.
  - honesty: Every noun has an overview verb, every verb takes --json, and adding a verb without a catalog entry, an overview `_VERBS` line and a learn mention fails a lockstep test; teken cli doctor . --strict passes in CI.
- The explain catalog and every error remediation point at the owning upstream page rather than restating it: docs/robot/cheatsheet.md (robotctl), docs/robot/duckctl.md, docs/policy-manifest.md, docs/design/architecture.md, `microduck_rl` AGENTS.md and scripts/hf/README.md. This honours upstream's own rule that one page owns a mechanism and everyone else says a sentence and points.
  - honesty: Each explain entry and each CliError remediation for a robot or training topic contains a URL into pollen-robotics/microduck or `microduck_rl` docs, and a test asserts no explain body restates a robotctl command table longer than three lines.
- The env noun brings up and checks the simulation stack by reproducing upstream's documented steps (or shelling out to scripts/duck-sim when the clone has it): clone/checkout microduck at sim-remote-io, 'cargo build -p robotd -p robotctl -p tof -p sounds', locate libonnxruntime in the `microduck_rl` .venv, generate a params toml naming the policy files from the clone, start 'duck-body' on a port then 'robotd --sim host:port --socket <state>/<name>.sock', wait for 'hello' + robot.health, and optionally 'robot.init'. It supports N ducks (one port each, one MuJoCo world), a scene (bare floor or apartment), headless mode, and a --fake backend for tests; 'env down' stops by pidfile after confirming /proc cmdline (upstream's `stop_one` lesson), never by name.
  - honesty: env up on a box with the two clones and a synced RL venv reaches robot.health healthy within 60 s on --fake and within 120 s on --sim; env down leaves no robotd, duck-body or tofd process and never signals a pid whose /proc cmdline does not match.
- The engine package (`microduck_cli`/behavior/ or engine/) mirrors reachy-mini-cli's shape so it can be extracted: engine.run(`tick_seam`=…) with a TickBus of drivers; a pure data model (channels, StopClass priorities, Lifetime) with duck channels = the intent families robotd exposes (twist, head, body pose, mouth, sound, skill); SenseProviders fed from robot.subscribe/robot.state + robot.health polled at 2 Hz + tof.frame + chorale.heard (peek callables, \*`_age_s` freshness, None on failure); a TargetSink that emits intents through the JSON-RPC client; rules-as-data loaded in two layers; bounded lifetimes fail-closed; senselog drop reasons on stderr; a state.json heartbeat so a second engine process refuses early. No SDK, transport or CLI error type is imported below the composition root.
  - honesty: The engine adds no command filtering of its own: robotd's `cmd_alpha`/`head_alpha` EMA (0.2 default in deploy/robotd.toml) is treated as part of the plant, so a rule's step command arrives as the ramp the daemon documents.
- Instruction injection has ONE admission path: a KindRegistry-style registry that validates fail-closed and admits (a) intents fired by react rules and (b) ad-hoc intents an agent or human sends via a CLI verb (e.g. 'duck intent <kind> …' / a spool file) — same validator, same bounds (duration caps, per-axis limits, cooldowns), same named refusals. Rules are the durable form of an instruction; an ad-hoc intent is the one-shot form. Every admitted instruction becomes robotd intents that robotd's own safety may still refuse, and the refusal is surfaced by name.
  - honesty: One KindRegistry instance serves both rule-fired and CLI-injected intents: a test injects the same over-limit payload by both paths and gets the same refusal text; a static check finds no second validator.
- The train lane targets three local hosts (DGX Spark GB10, Jetson Thor, Jetson AGX Orin) plus Hugging Face Jobs, and its env doctor detects which it is on (uname -m, nvidia-smi / JetPack markers, CUDA version) and reports whether `microduck_rl`'s pinned torch source applies. wandb is optional: the lane runs without a key and only passes --wandb-run-path / forwards a key when configured.
  - honesty: env doctor on GB10, Jetson Thor and AGX Orin prints the detected host class and whether `microduck_rl`'s torch source applies; with no wandb key the smoke test still runs and play/export accept a local checkpoint path.
- This repo's CLAUDE.md and README are updated in the first engine PR to record decision c20: the engine lives here for now, is built extraction-first, and neurosymbolic-system is the later home — replacing the current 'a tick loop here belongs upstream' guidance so a reviewer does not reject the engine on stale instructions.
  - honesty: The first engine PR's diff touches CLAUDE.md's neurosymbolic-system section and cicd/SKILL.md's triage defaults, replacing the 'engine belongs upstream' guidance with the extraction-first decision.
- The engine yields to a human driver. robotd applies intents last-writer-wins with no arbitration between clients, and padd (gamepad), the mediad console and a second CLI all send the same robot.move/head/pose notifications. The engine therefore watches pad.input (padd's raw tap) and robot.remoteSessionActive, and while a human is driving it inhibits its own continuous intents (a named 'human-driving' drop) — rules that fire a discrete skill are still admitted but robotd's refusal, if any, is surfaced by name.
  - honesty: With a --fake daemon and a simulated pad.input stream, the engine's call log shows zero robot.move/head/look/pose/do/setMode calls while the pad is active and a human-driving drop count on stderr; sound and mouth calls continue.
- 'robot.enable' is part of the gated-motion set alongside init/relax/do/move/mode (it 'can bring a limp robot up as a side effect of being asked to drive'), and the engine's start sequence is explicit: connect → hello (API version) → health → init (gated) → enable (gated) → rules armed. A skill fired by a rule while the robot is not driving is refused by robotd ('press Start first'); the engine surfaces that as a named drop rather than retrying.
  - honesty: A rule that fires a skill before enable produces a named drop and no retry; init and enable each pass the three gate tests of c7; the engine's start log shows the six steps in order.
- 'rules check' validates every action a rule names against what THIS duck actually has: the skill list comes from robot.policies at check time (or from a recorded skills snapshot for offline checks), a rule naming a missing skill is reported by id with the robot's list — the same behaviour upstream gives a pad binding for a skill the robot does not have. Skill names are never assumed from a static table.
  - honesty: rules check against a --fake daemon reporting skills \[a, b\] refuses a rule naming c with 'c not in \[a, b\]' and the rule id; --replay with a recorded skills snapshot gives the same answer offline.
- Own what you energize: on any abnormal engine exit (exception, Ctrl-C, socket error) the engine best-effort sends robot.stop, robot.pose {active:false}, robot.mouth 0 and robot.sound hold:false, each independently so one failure does not skip the rest, then exits non-zero naming what it could not send. It does NOT relax the robot (a deliberate hold must survive; relax collapses it). A dead socket is stated as the limit: robotd's own deadman zeroes velocity, but a held pose/mouth outlives us until its notification expires.
  - honesty: Killing the engine with SIGINT mid-behaviour against a --fake daemon yields exactly stop, pose active:false, mouth 0 and sound hold:false in its call log, no relax, and a non-zero exit naming any release that failed when one is forced to fail.
- The JSON-RPC client is a background I/O thread pair (writer with a bounded outbound queue; reader correlating replies by id and fanning notifications such as robot.state to peek slots). The tick thread only does `put_nowait`: a full queue, a wedged socket or a slow daemon resolve to a named drop ('ipc-queue-full', 'ipc-down'), never to a blocked tick. Requests from verbs (do/look/init) wait on their own future with a timeout; notifications are fire-and-forget.
  - honesty: A test that wedges the fake socket shows the tick period unchanged (measured over 100 ticks) and an ipc-down drop; a test that fills the queue shows an ipc-queue-full drop and no blocked tick.
- The shipped default rules are few and safety-first, mirroring `default_rules.toml`'s discipline: an inhibit rule that disables every skill and the idle base while robot.state reports fallen (recovery is the daemon's/VelStand policy's job), a low-battery inhibit keyed on robot.health's charge fraction, and at most one or two reactions that are obviously correct in any room. Rule ids are a public interface pinned by a test; everything else is the operator's overlay.
  - honesty: The shipped rules file contains at most four rules; a test pins their ids; a replay of a recorded fall shows every skill and the idle base inhibited within one tick of fallen=true.
- 'duck record' captures robot.state (via robot.subscribe), robot.health polls, pad.input and tof.frame to JSONL with monotonic timestamps — the artifact 'rules check --replay' and the engine's offline tests consume, and the source of truth for the duck sense-field vocabulary (resolving the parked unknown about the state payload). Stdout stays pure JSONL; all diagnostics go to stderr.
  - honesty: duck record against --fake writes one JSON object per line with a monotonic timestamp and source tag; stdout contains nothing but JSONL; rules check --replay accepts that file.
- rules.toml carries a `schema_version`; the loader refuses an unknown or missing version fail-closed with the fix named. This is what lets the schema move to neurosymbolic-system later without silently reinterpreting an operator's overlay.
  - honesty: A rules.toml without `schema_version` or with an unknown one is refused with the expected version named; the shipped layer and every fixture carry the current version.

## Scope / boundaries

- No motor is ever commanded except as an intent through robotd's JSON-RPC (robot.move/head/look/do/init/relax/stop/setMode/loadPolicy). robotd is authoritative on safety (architecture.md §1.1 invariant 2: fall detection, joint/thermal limits, deadman, safe pose) and is the only process on the Dynamixel bus; microduck-cli never opens the serial port, never bypasses a clamp, and treats a refused intent as the correct answer.
- `microduck_rl` is orchestrated as a sibling checkout via subprocess ('uv run --project <path> …'), never added as a dependency or extra of microduck-cli: its dependency tree (mjlab, warp, torch+CUDA, bam from git, requires-python <3.13) must not enter this package's resolution. Base runtime deps stay \[\] (CLAUDE.md hard constraint); if a hardware library is ever needed it goes behind an extra with a lazy import.
- microduck-cli never writes /etc/robot/robotd.toml or the params file of a running daemon: policy slots change only through robot.loadPolicy / robotctl policy (robotd writes the key under a file lock), pad bindings only through pad.bind, config only through robotctl configure. The CLI surfaces upstream's durability verbatim — a policy load 'survives a reboot and survives updates'; 'policy reset' puts it back — so a trial never silently becomes the boot default without saying so.
- No secret ever reaches stdout or a --json payload: `HF_TOKEN`, wandb keys, `DUCK_PIN` and the sim's account token file are reported as set/unset by 'env doctor' and never echoed; the train lane passes them by environment to subprocesses, never on a command line (visible in /proc cmdline).

## Non-goals

- No code is copied, vendored or cited from pollen-robotics/microduck or `microduck_rl`. The CLI implements against their documented surfaces — robotctl/duckctl verbs (docs/robot/cheatsheet.md, duckctl.md), the JSON-RPC method names in duck-ipc-proto/src/lib.rs, and `microduck_rl`'s 'uv run train/play/publish' + scripts/export.py — and links users to those docs rather than restating them.
- No training code lives here: no env cfgs, reward functions, MDP terms, MJCF models, exporters or publishers. Those are `microduck_rl`'s (src/`mjlab_microduck`/tasks, export.py, publish/); the CLI wraps, sequences and explains them. Likewise no policy files are bundled — policies come from the Hub (pollen-robotics/microduck-policies or a community repo) or the trainer's own export.
- No language model sits inside the rules layer's decision path. Agents (any backend) drive the CLI from outside — authoring rules, choosing skills, starting training — and the rules evaluator stays symbolic and model-free, machine-checkable the way reachy-mini-cli's tests/`test_zero_llm_boundary.py` checks it.

## Assumptions

- Sim-through-the-daemon is available today by building the microduck 'sim-remote-io' branch: docs/design/simulation.md on that branch reports 'working end to end for one duck' — robotd holds 50.0 of 50.0 Hz against a MuJoCo body, detects a seated boot, and 'robotctl robot init' stands the duck up. The stack is: `microduck_rl` 'uv run duck-body \[--ducks N --port 7801 --headless\]' + 'robotd --sim 127.0.0.1:7801 --socket <short path> --params <generated toml>' (ort dlopens libonnxruntime from the RL venv; policies are named in the params file) + robotctl/our CLI on that socket. 'robotd --fake' (a robot made of nothing, no physics) is the CI-grade backend. Risks: the branch is 32 ahead / 87 behind main and unmerged; containers, ether, camera and ToF are 'designed and measured but not built'. scripts/`infer_policy.py` remains the no-daemon fallback.
- Upstream's autonomous brain is unported: roadmap M9 says the prototype's autonomous.rs (in the private `microduck_runtime`, not a public repo) 'exists nowhere in the daemon' and it 'gets a design doc before it gets code'. So today the daemon offers policies, skills, safety and intents but no idle behaviour. The rules layer + engine in this repo therefore IS the duck's off-board behaviour for now, sending intents robotd may refuse; when M9 lands, the engine's rules become a layer above upstream's brain (inputs: chorale beacons/RSSI, ToF, sound events) rather than its replacement — the seam is the intent API either way.
- The development box is a DGX Spark GB10 (linux-aarch64, CUDA 13.0, driver 580.126) — exactly the ARM configuration `microduck_rl` documents (torch cu129 index, `UV_HTTP_TIMEOUT`=600 on first sync). hf auth is present (user orinachum), cargo/rustc are installed (duckctl is buildable), Python 3.12 is available via uv. Not present: a wandb ~/.netrc, any `DUCK_ROBOT`/`DUCK_HOST` setting, a duck in Bluetooth range or ssh config — so 'we have a duck, a communication with it' is not yet observable from this machine and the address/transport must come from the user.
- One engine process per duck, addressed by name → socket; N ducks in one MuJoCo world means N engines and N rules overlays. Cross-duck coordination (the chorale's beacons, duck-ether, follow-the-leader) is out of scope for v1 — those inputs arrive later as chorale.heard sense fields, not as a multi-duck engine.
- The engine ships one PASSIVE base behaviour (the duck's 'feel-alive': small robot.head / robot.look motions, occasional robot.sound chirps) so a duck with an armed engine is visibly alive between rules; it contributes only while the robot is driving and upright, and any admitted rule behaviour owns its channels over it.

## Decisions

- There is no Radxa board and no physical duck yet. The target is the SIMULATED duck: `microduck_rl`'s 'duck-body' (MuJoCo) driven by the real 'robotd --sim' from the microduck 'sim-remote-io' branch, reached over robotd's unix socket exactly as a real duck would be. duckctl is not the transport — it is a BLE client for a real duck's btd and has no equivalent in sim; the CLI talks JSON-RPC to robotd's socket directly.
- microduck-cli implements its own engine, following reachy-mini-cli's seams (one 50 Hz-class tick, `tick_seam`/TickBus fan-out, SenseProviders as injected peek callables, a TargetSink, rules as data, one admission registry for rule-fired and agent-injected intents, heartbeat-based liveness, named senselog drops). The duck stays as autonomous as upstream makes it, and this engine is a rules layer ABOVE it that injects instructions; an agent can inject ad-hoc instructions through the same path or author rules that do. neurosymbolic-system is then built by extracting from BOTH reachy-mini-cli and this engine, and this repo refactors to import it. This supersedes the CLAUDE.md line that says an engine loop here belongs upstream.
- Training runs locally OR on Hugging Face Jobs, selectable per run. Local targets to support: DGX Spark (GB10), Jetson Thor, and Jetson AGX Orin. wandb is optional and configurable — never required for the lane to work.
- Human-driving gate (q4, option B): while pad.input or robot.remoteSessionActive shows a human, the engine withholds every body-moving intent (twist, head, look, pose, skills, mode) as a named 'human-driving' drop and keeps the non-motion channels (robot.sound, robot.mouth), recording and rule evaluation live; the engine never overrides a person — robotd's deadman, clamps and fall reflex are the safety layer under a human driver.
